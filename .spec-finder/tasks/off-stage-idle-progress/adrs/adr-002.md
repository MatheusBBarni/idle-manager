# ADR-002: Off-screen park, spike-gated keep-alive

## Status

Accepted

## Date

2026-09-01

## Context

PRD ADR-001 requires invisible keep-alive: running accounts keep idle progress when off-stage (another game tab) or hidden under a confirm dialog, without new chrome, inject, always-paint, or a RAM diet. Today `applyStage` calls `setVisible(false)` in those cases. Electron documents window-level Page Visibility when `backgroundThrottling` is false, not view-level `setVisible`. Public IPC and the workspace snapshot stay unchanged.

This ADR records the implementation approach. It does not change product scope.

## Decision Drivers

- PRD: G-01, G-02, F-01–F-06; overlay may hide for chrome but must not freeze
- User: no IPC or snapshot change
- User: spike-gated production hide; if no knob passes, leave `applyStage` as today and stop (no inject, no always-paint)
- User: local fixture on the implementer host (Darwin OK); Windows in-game journal remains G-01/G-02
- User: design A — prefer off-screen park; spike vs current hide and vs `removeChildView`
- Repository: Vitest is `src/shared` only; `verify:isolation` is the Electron gate; game `executeJavaScript` is forbidden
- Official docs: `View.setVisible` has no Page Visibility contract; throttling-off is window-global since Electron 28

## Decision

Implement V1 as:

1. A shared `gameViewPlacement` predicate (paint vs park vs omit) derived only from existing `StageReport` + popped-out + live running. No IPC, no snapshot fields.
2. A local-origin fixture (not a game) that measures `document.visibilityState`, `setInterval`, and whether the view covers stage/overlay.
3. Knob order: **baseline** current `setVisible(false)`; **park** off-chrome bounds, `setVisible(true)`, stay a `contentView` child, contents ≥ 8×8; **detach** `removeChildView` without `setVisible(false)`.
4. Production `applyStage`: if baseline already passes the fixture, do not change hide. If baseline fails, ship **park** if it passes, else **detach** if it passes, else **no production change** and stop (product ADR). Chromium switches and game `backgroundThrottling: false` stay. Close remains `destroyView`.

## Alternatives Considered

### Detach-first (approach B)

- **Benefits:** Matches the RAM packet’s don’t-paint knob; may drop compositor cost
- **Costs/risks:** Visibility never measured; may still look hidden; confuses freeze-fix with diet
- **Why not selected:** User chose park-first; RAM diet is out of this packet

### Flags only (approach C)

- **Benefits:** No `applyStage` risk
- **Costs/risks:** Current hide is the freeze surface; flags already on
- **Why not selected:** User chose A; C would likely fixture-fail and ship nothing without trying park

### Visibility-probe IPC / `executeJavaScript` on games

- **Benefits:** Chrome could show ticks
- **Costs/risks:** New contract; game inject forbidden; G-03 no new chrome
- **Why not selected:** User chose no IPC

## Consequences

### Positive

- Other-tab and overlay share one placement rule
- Overlay chrome stays usable (views not painted on-stage)
- Cannot ship a freeze “fix” that still reports `hidden` on the fixture

### Negative and trade-offs

- Production hide waits on a fixture; packet may stop with no `applyStage` change
- Fixture can pass while a Windows game still self-pauses (journal is still G-01)
- Park keeps views in the tree (RAM not improved)

### Risks and mitigations

- Park still `hidden` — try detach; if both fail, stop
- Tiny-bounds path (`< 8px`) also hides today — park uses ≥ 8×8
- Isolation regression — `pnpm verify:isolation` when `views.ts` changes
- Game inject temptation — fixture only, local origin

## Reversibility and Rollback

- Revert `applyStage` independently of chrome
- No schema/IPC to migrate
- Predicate can stay even if production paint reverts

## Implementation Notes

- Do not edit `workspace.ts` / `parseSnapshot`
- Do not add `popoverOpen` or metrics IPC for this packet
- Do not remove Chromium anti-throttle switches
- Do not call game `executeJavaScript`
- Do not treat RAM Task Manager drop as a pass criterion
- Single-layout no-panel accounts may park via the same path; they are not the success gate

## Follow-ups

- Fixture journal before production `applyStage`
- Windows G-01/G-02 in-game journal after a shipped knob (not CI)
