# ADR-001: Invisible keep-alive, same workflow

## Status

Accepted

## Date

2026-09-01

## Context

A shared-Windows operator who tiles about 3–6 isolated idle-game logins starts accounts, leaves them **running**, then switches to another game tab or opens a confirm dialog. Those views stay in the live map (close was not used) but leave the stage or are hidden so chrome can cover the stage. Idle progress then stops. Isolation already uses one persist jar per account. Machine cost is a separate packet (`running-session-performance`). Chrome Memory Saver, auto-sleep, Park, merged jars, and gameplay bots are out.

This ADR records the product approach for `off-stage-idle-progress`. It does not lock view, visibility, or process implementation.

## Decision Drivers

- User: the failure is freeze of idle progress, not RAM
- User: primary operator is a small live farm (about 3–6 accounts, one or two games) on a shared Windows PC
- User: success is a before/after Windows game journal (3-account and 6-account); 0 freeze/reload while another tab is focused; overlay hide must not freeze either
- User: no new chrome; operator learns by looking at the game later
- User: auto-sleep, discard/reload, Park, merged jars, bots, inject, painting games over modals, single-layout/minimize as the gate, and macOS as the gate are out
- User: selected approach A — invisible keep-alive, same workflow
- Repository: running views are hidden with `setVisible(false)` off-stage and when `overlayOpen`; they are not destroyed until close
- External: Page Visibility and timer throttling commonly pause hidden pages; Memory Saver reloads discarded tabs; Electron documents window-level visibility when throttling is off, not view-level `setVisible`

## Decision

V1 keeps the existing start / close / tile / tab / dialog workflow. Every account left **running** must keep idle-game progress when it is off-stage (another game tab) or hidden under a confirm dialog. Returning to it is not a fresh load. Close remains the explicit stop. Isolation stays one persist jar per account. No new live-cue chrome.

Out: RAM diet, Chrome Memory Saver, auto-sleep, named Park, merged jars, bots, injecting into game pages, painting running views over modals, single-layout or minimized-window freeze as the success gate, macOS/Linux as the success gate.

## Alternatives Considered

### Always-painted farm (approach B)

- **User value:** Games that self-pause on hidden never see hidden
- **Costs/risks:** Game views paint above HTML; dialogs fail or games cover them
- **Why not selected:** User chose A; overlay hide is required for chrome that covers the stage

### Journal-gated fail-closed (approach C)

- **User value:** No fake “fixed” if idle still stops
- **Costs/risks:** Packet can ship nothing while freeze remains
- **Why not selected:** User chose A; freeze is the failure to solve, not an optional diet

### RAM quieter-farm (`running-session-performance`)

- **User value:** Shared PC stays usable
- **Costs/risks:** Different failure; Windows diet spike never ran
- **Why not selected:** User chose freeze as this packet’s problem; cost stays a separate packet

## Consequences

### Positive

- Multi-tab farm is actually a farm (G-01)
- Confirm dialogs do not tax idle time (G-02)
- Operator learns no new verbs (F-06)

### Negative and trade-offs

- No chrome signal that off-stage accounts are still live
- Single-layout siblings and minimized windows can still freeze after V1
- Games that self-pause on `document.hidden` may still fail the journal if hide still looks hidden to the page

### Risks and mitigations

- View hide still reports hidden to the game — Journal is G-01/G-02; do not declare success from fixture timers alone
- Temptation to inject into the game — Out of scope; stop and new ADR if only inject would work
- Temptation to always-paint over dialogs — Forbidden by this ADR; overlay chrome stays usable

## Reversibility

- Hide policy can revert without touching partitions or close
- Evidence that would trigger revisit: Windows journal where other-tab accounts still freeze after V1, or operators demand a live cue because they cannot tell
- Promote single-layout or minimize only with a new ADR
