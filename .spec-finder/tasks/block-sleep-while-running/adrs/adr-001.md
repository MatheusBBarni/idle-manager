# ADR-001: Running-bound keep-awake

## Status

Accepted

## Date

2026-09-01

## Context

A Windows desktop operator tiles about 3–6 isolated idle-game accounts and leaves them running overnight or AFK. Idle manager already keeps those Chromium views live (no background throttle). Windows can still sleep on its idle timer, which stops ticks. Close already drops a live view; a named Park that stops ticks is out. The operator asked to block OS sleep while any account is running, show a chrome hint, and allow sleep again when every account is closed — without forcing the window to stay visible, without bots, and without changing isolation.

## Decision Drivers

- Need: overnight/AFK ticks die because Windows slept, not because a panel was parked
- Users: Windows desktop, ~3–6 accounts; lid-close laptops and always-on boxes are not the V1 gate
- Success: before/after overnight dogfood journal over 1–2 weeks; no telemetry
- Non-goals: display-forced-on, Settings toggle, timed keep-awake, power-plan editor, lid-close / Start→Sleep defeat, macOS/Linux as success gate
- Chrome: status-bar hint only; no covering modal, no tray, no Settings row
- Smallest approach that satisfies the need: automatic bind to running accounts

## Decision

V1 **automatically blocks Windows sleep while any account is running** (including other-tab, popped-out, and minimized window), shows a **status-bar hint** that sleep is blocked, and **releases the block when every account is closed** (or the app is no longer running). The screen may turn off. The window need not stay visible.

Out: display-forced-on, arm/disarm toggle, timed keep-awake, changing the Windows power plan, defeating lid-close or Start→Sleep, macOS/Linux as the success gate, named Park, bots, covering chrome.

## Alternatives Considered

### Opt-in overnight arm (approach B)

- **User value:** A daytime Start on a shared desktop does not keep the PC up
- **Costs/risks:** Forgetting to arm recreates the overnight failure
- **Why not selected:** User chose A; the verified need is automatic while any account is running

### Keep-awake and keep the display on (approach C)

- **User value:** Display/GPU-bound idle loops are less likely to pause
- **Costs/risks:** Bright monitor all night on a shared desktop
- **Why not selected:** User chose A; non-goals already excluded display-forced-on

## Consequences

### Positive

- Overnight/AFK farm is not killed by the Windows idle sleep timer
- Operator can see the block without a covering overlay
- Closing the last account (or quitting) returns normal sleep

### Negative and trade-offs

- A live farm can hold the PC up all night on a shared desktop
- Monitor-off may still pause some games
- Lid close, lock screen, and Start→Sleep are not defeated

### Risks and mitigations

- Stuck keep-awake after last close — G-03 journal; release on zero running and on quit
- Operator never looks at the status bar — accepted; extra chrome was rejected
- Monitor-off pauses a title — out of V1; reconsider display-on only with a new ADR if the journal shows that failure

## Reversibility

- Drop the keep-awake request and the hint without touching isolation or running/closed semantics
- Revisit display-on or an arm control only with a new ADR if the journal shows monitor-off pauses or shared-PC complaint
- Evidence that would trigger revisit: nights where the PC stayed on but idle froze after screen-off, or household complaint that a daytime Start held the PC up
