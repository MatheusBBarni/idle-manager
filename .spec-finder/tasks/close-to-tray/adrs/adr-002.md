# ADR-002: Hide-in-place tray session

## Status

Accepted

## Date

2026-09-01

## Context

Product ADR-001 requires win32 Close with a live farm to dismiss chrome off the desktop and taskbar without stopping running accounts. `syncViews` parents every `WebContentsView` to one chrome `BrowserWindow` and no-ops if that window is gone. Destroying chrome cannot keep ticks. Electron 37 has Tray tooltip/menu and `setSkipTaskbar`, but no Windows tray badge. `quitAndInstall` emits window `close` before `before-quit`. There is no single-instance lock today.

## Decision Drivers

- G-01 / G-02 / F-01: dismiss without destroying views
- F-03: running count without restoring (tooltip is the smallest Electron API)
- US-04: Settings and tray Quit via one `beginQuit` seam
- Partition safety: two processes must not open the same `persist:` jars
- Fail closed if Tray cannot be created
- win32-only success gate (ADR-001)

## Evidence

| Kind | Finding | Source | Version/date |
|---|---|---|---|
| Repository | `syncViews` requires a live chrome window | `src/main/views.ts` | 2026-09-01 |
| Official docs | `close` preventDefault, `hide`, `setSkipTaskbar`; Tray tooltip | Electron 37.10.3 | 37.10.3 |

| User decision | Approach A hide+tooltip; `WindowCommand` `'quit'`; app-wide lock; fail-closed; win32 only | TechSpec clarification | 2026-09-01 |

## Decision

V1 on **win32** keeps the existing chrome window:

- `shouldDismissToTray` is true only for `win32` && !quitting && trayReady && runningCount > 0.
- Those Closes `preventDefault`, `hide()`, `setSkipTaskbar(true)`, and show a Tray with tooltip count and Restore/Quit.
- `beginQuit()` (Settings `windowControl('quit')`, tray Quit, updater Apply) sets quitting then exits so Close is not intercepted.
- No Tray → Close behaves as today (quit).
- `requestSingleInstanceLock`: second process exits; first restores or focuses.
- darwin/linux Close/quit unchanged. No snapshot field. No drawn glyph. No new dependencies.

## Alternatives Considered

### Drawn count on the tray image

- **Benefits:** Count visible without hover.
- **Costs/risks:** NativeImage work not covered by Vitest.
- **Why not selected:** User rejected approach B.

### Destroy chrome and rehost views

- **Benefits:** True window close.
- **Costs/risks:** Reparent/reload vs G-02; fights `syncViews`.
- **Why not selected:** User rejected approach C.

### No single-instance lock

- **Benefits:** Matches today’s multi-process launches.
- **Costs/risks:** Second launch while dismissed opens the same partitions.
- **Why not selected:** User selected app-wide lock.

## Consequences

### Positive

- Views stay parented; ticks can continue.
- One Quit seam unblocks Apply update.
- Shared policy is unit-testable without Electron.

### Negative and trade-offs

- Count is tooltip-only (overflow/hover).
- App becomes single-instance on all OSes that get the lock (lock is process-wide; Close-to-tray remains win32).
- macOS/Linux Close still destroys views.

### Risks and mitigations

- Tray construct fails — fail closed (quit).
- Apply stuck behind preventDefault — Apply must call `beginQuit` first.
- Keyboard restore — accepted in PRD; second-instance restore is an extra path.

## Reversibility and Rollback

- Remove close interceptor, tray helper, `'quit'`, and the instance lock. Additive IPC. No disk migration.

## Implementation Notes

- Do not null `chromeWindow` on hide. Do not call `destroyAllViews` until a real quit.
- Do not add tray account actions. Do not persist dismissed. Do not add packages.
- i18n keys `quit` and `trayRestore` in all four dictionaries.
- `pnpm verify:isolation` only if partition/session/view isolation paths change.
