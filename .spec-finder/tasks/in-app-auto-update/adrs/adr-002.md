# ADR-002: Chrome-strip Apply/Later MVP

## Status

Accepted

## Date

2026-08-30

## Context

ADR-001 already locks Windows-only, operator-timed obtain+apply, with Authenticode as a V1 ship gate. The remaining product choice is how the operator is told a version is ready, how hard V1 may interrupt a live farm, and whether the marketing site or a feed-only phase is in MVP.

A live farm is painted in game panels above chrome. Existing dialogs hide those panels. WCAG 2.2.4 (AAA) asks that non-emergency interruptions can be postponed. The locked persona is mid-session: do not close the farm now.

## Decision Drivers

- Success is dogfood obtain+apply on the first 1–2 signed Windows releases, with a chosen restart and surviving accounts/layout — not adoption speed, not a failure-retry ship gate.
- User cut blocking restart overlays, Settings “check now,” and nagging after Later.
- User chose a non-covering chrome strip for Apply/Later, silent chrome unless a signed Windows update is actually ready, and Later = hide for the rest of this session (may return next launch).
- Website cutover copy and feed-first-without-Apply were offered and rejected.

## Decision

V1 is the **chrome-strip MVP after signing exists**.

- Background obtain on Windows once a signed feed exists.
- Quiet “getting update” on the chrome strip while obtaining.
- When ready: Apply and Later on that strip, without covering game panels.
- Later hides Apply for the rest of the session; the same ready state may return on the next launch.
- Apply is the operator-chosen restart. Accounts and layout must survive.
- Chrome stays as today (version only) when V1 cannot apply: already latest, macOS/Linux, unsigned build, or failed obtain.
- Out of this approach: Settings check-now, blocking overlay, nag after Later, failure copy, mac/Linux installer hint, extra website campaign.

Unsigned 0.2.0 operators still install the first signed Windows build once via the existing download path. That last installer is a known cost, not a V1 website project.

## Alternatives Considered

### Strip plus website cutover copy

- **User value:** Explains that today’s unsigned Windows operators must install once more.
- **Costs/risks:** Grows V1 onto the marketing site; easy to mix up with mac/Linux installer messaging.
- **Why not selected:** User chose A; landing already warns about unsigned/SmartScreen.

### Feed-first, chrome later

- **User value:** Prove the signed feed before any in-app Apply.
- **Costs/risks:** First signed tag is still an installer hunt; locked success bar waits on a second phase.
- **Why not selected:** User chose A; `_idea.md` already rejected deferring Apply chrome as V1.

## Consequences

### Positive

- Farm stays visible while a version is ready.
- Smallest chrome that still meets dogfood obtain+apply.
- Authenticode gate unchanged.

### Negative and trade-offs

- Apply is easy to miss during play.
- Failed obtain looks like “no update.”
- 0.2.0 → first signed build remains an installer, unexplained beyond existing site copy.

### Risks and mitigations

- Nobody notices Apply — dogfood G-01 fails; reconsider overlay-once (rejected B) only with a new ADR.
- Signing never purchased — V1 does not ship (ADR-001).
- Next-launch return of Apply feels like a nag — dogfood; do not add mid-session nag without a new ADR.

## Reversibility

- Chrome copy and Later rules can change without reopening Authenticode.
- Adding website cutover copy later does not require undoing the strip.
- Feed-only would be a step backward from the locked success bar.

## Follow-ups

- Dogfood whether session-Later + next-launch return is enough to hit G-01.
- Per-user vs per-machine Windows installs remain an open (non-blocking) question for TechSpec/ops.
