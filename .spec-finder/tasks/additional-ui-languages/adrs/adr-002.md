# ADR-002: Widen the existing chrome locale seam

## Status

Accepted

## Date

2026-08-31

## Context

Approved `_prd.md` requires complete Spanish and Simplified Chinese chrome in one V1, a Settings picker, page language that follows chrome, default generated account names, and no change to isolation or game documents.
Product ADR-001 already locked that scope.

Today locale is `'pt' | 'en'` on the workspace snapshot, dictionaries live in `src/shared/i18n.ts`, `parseSnapshot` keeps only `'en'` else `'pt'`, and non-`pt` means English in `App.tsx` and `nextAccountName`.
A design is needed so new tags survive reload without a new i18n stack.

## Decision Drivers

- G-01, G-02, F-01, F-02: complete chrome dictionaries
- F-03: Settings choices, names in their own language
- F-04, US-07: `html lang` follows chrome
- F-07, US-08: generated account names follow locale
- G-04, F-06: locale change must not touch sessions
- User decision: persisted union `'pt' | 'en' | 'es' | 'zh-Hans'`
- User decision: invalid `prefs/locale` no-ops; unknown disk locale still becomes `'pt'`
- User decision: Vitest on `src/shared` plus `pnpm test` and `pnpm typecheck`
- AGENTS.md: workspace mutations in `applyAction`; Vitest only `src/shared`

## Decision

Keep the current locale seam and widen it.

- `Locale` is `'pt' | 'en' | 'es' | 'zh-Hans'`.
- Dictionaries stay in `src/shared/i18n.ts`.
- `parseSnapshot` accepts that allowlist and maps anything else to `'pt'`.
- `prefs/locale` no-ops when the payload is not a `Locale`.
- `t()`, `nextAccountName`, Settings, `html lang`, and HeroUI `I18nProvider` all consume `Locale`.
- Game `WebContentsView` sessions do not get a chrome-driven language override.
- No new package, directory, or translation runtime.

## Alternatives Considered

### One module per locale

- **Benefits:** Smaller files as languages grow.
- **Costs/risks:** Extra modules for about 80 keys.
- **Why not selected:** User chose the existing single-module seam.

### Translation runtime (JSON packs or i18next)

- **Benefits:** Fallback chains and extraction tooling.
- **Costs/risks:** New dependency; no extra PRD coverage.
- **Why not selected:** Conflicts with preferring existing modules.

## Consequences

### Positive

- `es` and `zh-Hans` round-trip on disk.
- PT and EN files stay valid with no migration.
- Isolation and game documents stay out of the change.

### Negative and trade-offs

- `i18n.ts` grows by two full dictionaries plus language-name keys.
- Traditional Chinese later is a new tag (`zh-Hant`), not a rename of `zh-Hans`.

### Risks and mitigations

- Incomplete dictionary offered as a language - `Record` typing plus Vitest; do not add the Settings button until tests pass.
- Junk IPC locale - reducer no-op.
- Game sites following chrome language - do not set partition `Accept-Language`.

## Reversibility and Rollback

- Hide a Settings button if a dictionary fails the checklist.
- Saved `es` / `zh-Hans` remain allowlisted; rollback of copy does not require a schema version bump.
- Reverting the union without an allowlist would make those files parse as `pt`.

## Implementation Notes

- Do not fork locale rules in React. Settings only dispatches `prefs/locale`.
- `Chrome.tsx` must use `Locale`, not `'pt' | 'en'`.
- New message keys `localeEs` and `localeZhHans` are allowed in PT and EN (G-03).
- Update the AGENTS.md i18n line so new keys are added to all four dictionaries.
- Do not edit `site/` locale types.

## Follow-ups

- Ship-time manual checklist remains G-01 and G-02 evidence that unit tests cannot prove.
