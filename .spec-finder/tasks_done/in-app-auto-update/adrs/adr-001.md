# ADR-001: Windows operator-timed in-app apply, Authenticode as V1 gate

## Status

Accepted

## Date

2026-08-30

## Context

Operators of Idle manager run many isolated accounts in one window. Today a new version means download an installer from GitHub Releases, quit the live farm, and run NSIS/DMG/AppImage. The locked product outcome is: obtain the new version while the app is running, apply it only when the operator chooses, and keep accounts/layout across that restart.

The repo already ships unsigned Windows NSIS, unsigned macOS DMG, and Linux AppImage. CI uses `electron-builder --publish never` and attaches only installers plus `SHA256SUMS.txt`. There is no updater client. electron-builder auto-update for this packager needs `latest.yml` and, on Windows, Authenticode verification (`verifyUpdateCodeSignature` defaults true). macOS auto-update requires a signed app and a zip for `latest-mac.yml`.

Independent critique split on whether V1 may disable Windows publisher checks to apply unsigned NSIS in-app (pragmatic + product) versus treating Authenticode as a ship gate (security + devil). That choice is consequential: in-app apply without publisher verification removes SmartScreen, the remaining OS publisher gate, and makes a compromised GitHub Release equal to code execution in the process that owns every `persist:opsource-account-*` jar.

## Decision Drivers

- User-approved V1 outcome: obtain while running, apply on operator-chosen restart; notify + traditional installer was rejected as V1.
- Ambition is a quick win: no channels, rollback UI, or staged rollouts.
- Windows is the primary packaging target (NSIS).
- Isolation of account partitions is the product; an updater that replaces main is a trust-root change, not chrome.
- electron-builder / Electron docs: macOS auto-update requires signing; Windows publisher-signature verification defaults on.
- Council Pass 2: security and devil held firm against disabling `verifyUpdateCodeSignature`; product partially conceded feed-before-chrome.

## Decision

V1 is **Windows-only, operator-timed in-app obtain and apply**, with **Authenticode as a ship gate**.

- The operator can fetch a new Windows version while the farm is running and apply it only when they choose to restart.
- CI must publish electron-builder GitHub update metadata (`latest.yml` and related NSIS artifacts) instead of `--publish never` as the only publish path.
- `verifyUpdateCodeSignature` stays enabled. V1 does not ship an in-app execute path on unsigned Windows builds.
- macOS and Linux stay on the existing installer path in V1.
- Auto-restart, force-latest, channels, staged rollouts, and rollback UI are out of V1.
- Notify-only (toast then traditional installer) is not V1.

If Windows Authenticode cannot be obtained, this V1 does not ship. That is a blocked dependency, not a silent pivot to unsigned apply.

## Alternatives Considered

### Unsigned Windows in-app apply now

- **Benefits:** Matches quick-win ambition without buying a cert; GitHub is already the first-install trust root.
- **Costs/risks:** Disabling publisher checks removes SmartScreen for updates; a stolen `GITHUB_TOKEN` or malicious release replaces the binary that owns every account jar.
- **Why not selected:** Security and devil held firm; user chose Hybrid over this original.

### Defer updater chrome until demand and a signed feed exist

- **Benefits:** Avoids RCE channel and dead UI against `--publish never`; audience is 1 star / two releases.
- **Costs/risks:** Every tag still interrupts the farm for an installer wizard; user already rejected notify+installer as V1.
- **Why not selected:** User chose Hybrid; the locked outcome is in-app obtain+apply, not installer-hunt.

### All-platform in-app update including macOS/Linux

- **Benefits:** One story on every OS the release workflow already builds.
- **Costs/risks:** macOS auto-update requires Developer ID + notarization + zip/`latest-mac.yml`; current mac target is unsigned DMG-only. Linux is not the primary packaging target.
- **Why not selected:** Conflicts with Windows-primary packaging and the quick-win ambition.

## Consequences

### Positive

- User-visible V1 still removes the installer hunt on Windows once signing exists.
- Account-jar trust root stays Authenticode, not “GitHub asset + same-job checksums.”
- Scope stays small: Windows, operator-timed, no channels.

### Negative and trade-offs

- V1 is delayed until paid Windows signing exists (exact Azure Artifact Signing price unknown this session).
- macOS and Linux operators keep downloading installers.
- `quitAndInstall` still tears down live `WebContentsView`s; V1 removes the wizard, not the restart.

### Risks and mitigations

- Signing never purchased — V1 does not ship; do not fall back to `verifyUpdateCodeSignature: false` without a new ADR.
- Per-machine NSIS / UAC (`allowToChangeInstallationDirectory: true`) may block silent apply — dogfood per-user vs per-machine; document if apply needs elevation.
- Chrome ships before `latest.yml` — treat unpublished feed as P0; do not ship Apply UI against `--publish never`.
- Compromised GitHub release even when signed — signing verifies publisher, not honesty of the GitHub account; protect `GITHUB_TOKEN` / release permissions as ops follow-up.

## Reversibility

- Reversible until the first signed updater-enabled build is in operators’ hands.
- After that, turning the client off still leaves signed NSIS as the installer path.
- Switching later to unsigned in-app apply would be a new trust-root ADR, not a tweak.

## Follow-ups

- Choose and obtain a Windows code-signing path (Azure Artifact Signing or equivalent); record vendor/price when known.
- Change the release workflow so Windows artifacts include `latest.yml` (and blockmaps if produced) on tagged releases.
- Confirm whether typical Windows installs are per-user or per-machine.
- macOS in-app update only after Apple Developer Program + zip target; separate ADR.
