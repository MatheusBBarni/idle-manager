# ADR-002: Tight loop plus Settings list and landing Keyboard section

## Status

Partially superseded by [ADR-004](adr-004.md) for the public-site lookup surface (landing section). Remaining in force: no-op without a tab; README + Settings list; no remapping; do not port all README shortcuts.

## Date

2026-08-30

## Context

`_idea.md` and ADR-001 already lock a mouse-free account loop (create with default name, next/previous, start) while a game panel is focused. The PRD still needed empty-path behavior, how operators learn the binds, and whether the public site grows a new page.

The player site is a dual-state **one** PT+EN landing, not a docs hub (product-website ADR-002). Plus is disabled without a tab. `Mod+T` already creates tabs.

## Decision Drivers

- User: no tab → account-loop keys have no effect; first-run stays New tab / `Mod+T`
- User: learn binds via README **and** a read-only list in existing Settings (PT+EN)
- User: public site should teach the loop
- User: PRD approach A — Keyboard **section** on the existing landing, not a new docs URL
- Website packet: one-page landing, not extra doc routes
- Quick-win ambition: no remapping, no start-all/stop, no porting every existing README shortcut

## Decision

V1 product approach is the **tight account loop plus in-product and on-landing lookup**:

1. Create, next/previous, and start remain the only new account actions. They work while a game panel is focused. Create uses the default name. Mouse Plus → name dialog stays for operators who want to name on create.
2. If there is no tab, those keys do nothing. They do not open New tab.
3. Operators can look up the three binds in the README Keyboard table **and** a read-only list inside existing Settings (Portuguese and English). No remapping.
4. The existing player landing (PT+EN) gains a Keyboard **section** that lists those three binds. No new docs URL and no docs hub.
5. Existing README shortcuts (reload, mute, URL bar, new tab, …) are not required to gain game-focused behavior in this PRD.

## Alternatives Considered

### Fall through to new tab when the loop cannot run

- **User value:** One key always “does something” on first launch.
- **Costs/risks:** One key, two jobs; surprises someone who meant to add an account.
- **Why not selected:** User chose no-op A; `Mod+T` already creates tabs.

### README only (no Settings, no site)

- **User value:** Smaller chrome and no website coupling.
- **Costs/risks:** Operators who never open the README never learn the loop.
- **Why not selected:** User chose Settings list and site teaching.

### New dedicated keyboard page on the site

- **User value:** Shareable docs URL.
- **Costs/risks:** Second public page; fights one-page site ADR.
- **Why not selected:** User chose approach A (landing section).

### Also make every existing README shortcut work while a game is focused

- **User value:** Reload/mute/URL-bar without clicking chrome.
- **Costs/risks:** Larger than the loop; delays the dogfood test.
- **Why not selected:** User rejected approach C; idea opportunity C was already rejected.

## Consequences

### Positive

- Lookup lives where operators already open Settings and where the landing is shared.
- Empty path matches today’s Plus-disabled behavior.
- Website stays one landing.

### Negative and trade-offs

- Landing gets longer; app PRD now has a website copy dependency (PT+EN).
- No standalone `/keyboard` URL.
- Operators who never open Settings or the site still need the README.

### Risks and mitigations

- Settings/landing lists drift from the real binds — same three actions in README, Settings, and landing; change them together.
- Overlay for Settings hides game views (existing rule) — accept; lookup is not done while playing in the panel.

## Reversibility

High. Settings copy and a landing section can be removed without taking the keys away. Removing the keys does not require keeping the lists.

## Follow-ups

- TechSpec: how keys reach a focused game panel (product constraint only: they must).
- Website packet: add the Keyboard section without turning the landing into a docs hub.
