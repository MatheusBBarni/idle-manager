# ADR-004: PT+EN keyboard docs pages (not a landing section)

## Status

Accepted

## Date

2026-08-30

## Context

ADR-002 locked public lookup as a Keyboard **section** on the existing player landing (PRD approach A). The operator later required a **docs page on the site**, not a section. product-website V1 is still one marketing landing; this packet now adds one extra locale-prefixed docs URL for the four loop binds.

Site routing already prefixes locales (`/idle-manager/en/`, `/idle-manager/pt/`) with `trailingSlash: always` (`site/astro.config.mjs`).

## Decision Drivers

- User: rewrite PRD, TechSpec, and tasks — docs **page**, not a landing section
- ADR-002 remainder: README + Settings list; no remapping; no-op without a tab
- Existing Astro i18n: new pages live under `src/pages/<locale>/`
- Do not grow a docs hub (changelog, full manual)

## Evidence

| Kind | Finding | Source | Date |
|---|---|---|---|
| User decision | Docs page in `site/`, not a Keyboard section | Explicit rewrite request | 2026-08-30 |
| Repository | Locales `/en/` and `/pt/`; pages mount layouts | `site/astro.config.mjs`, `site/src/pages/` | 2026-08-30 |
| Repository | Landing copy is `landing.ts` + `Landing.astro`; index pages only mount | `site/src/pages/en/index.astro` | 2026-08-30 |

## Decision

Public-site lookup for V1 is a **dedicated keyboard docs page** in both locales:

1. URLs: `{base}/en/keyboard/` and `{base}/pt/keyboard/` (today `https://matheusbarni.github.io/idle-manager/en/keyboard/` and `.../pt/keyboard/`).
2. Files: `site/src/pages/en/keyboard.astro`, `site/src/pages/pt/keyboard.astro`, copy in `site/src/content/keyboard.ts` (not `landing.ts` bind lists).
3. The page lists the same four frozen chords as Settings and README. PT and EN.
4. The existing landing may **link** to that page (nav). It must not embed the bind list as a landing section.
5. No further docs routes in this packet (no changelog, no `/docs` index, no English-only page).

This supersedes ADR-002 decision (4) and the rejected “new dedicated keyboard page” alternative.

## Alternatives Considered

### Keyboard section on the landing (ADR-002)

- **User value:** No second URL; one-page site discipline.
- **Costs/risks:** Operator asked for a shareable docs page, not in-page copy.
- **Why not selected:** Explicit rewrite: not a section.

### Full docs hub (`/docs`, multiple articles)

- **User value:** Room for later shortcuts.
- **Costs/risks:** Contradicts quick win and product-website “one player page” for marketing.
- **Why not selected:** One keyboard page only.

## Consequences

### Positive

- Shareable PT and EN URLs for the four binds.
- Landing stays a player/marketing page.

### Negative and trade-offs

- Second public URL per locale; product-website “no extra URLs” is overridden for this one path.
- Four surfaces to keep in sync: matcher, Settings, README, docs page.

### Risks and mitigations

- Landing visitors never find the page — add a Keyboard nav link on the landing (not a bind list).
- Copy drift — same four accelerators as ADR-003.

## Reversibility

High. Delete the two pages and content module; remove the landing nav link. Keys in the app stay.
