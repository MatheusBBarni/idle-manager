# ADR-001: Mouse-free account loop during real play

## Status

Accepted

## Date

2026-08-30

## Context

Idle manager already has chrome keyboard shortcuts (new tab, reload, mute, zoom, tab cycle, `Mod+1…9` account jump). The operator pain is the **account loop**: create an account, move to the next/previous account, and start/run it. Those three actions are mouse-only today (sidebar Plus + name dialog; dropdown / double-click / empty-stage CTA / start-all).

The success bar is a one-week dogfood: a shortcut-aware multi-account operator completes create → cycle → run without the mouse for those actions. Game documents are `WebContentsView`s that paint above the React chrome. Independent critique agreed that extending the chrome `window` `keydown` listener alone makes that bar false once a panel is focused.

This ADR records the V1 product direction. It does not lock a class-level API.

## Decision Drivers

- User: pain is mouse trips for create / focus / run, not findability
- User: primary user is a multi-account operator during setup and cycling
- User: V1 action set is create, next/previous, run/start only
- User: ambition is a quick win, not a customizable command platform
- User: success is ~1 week mouse-free dogfood for those three actions
- User: direction A — loop must work while a game panel is focused; create uses default `Account N` / `Conta N`
- Repository: shortcuts exist but miss the loop; `account/create` starts `closed`; start is mouse-only; app menu is null
- Critique: chrome-only keydown fails after the first Start; intercept only allowlisted modifier chords
- External: Chrome-class reserved `Ctrl`/`Cmd` chords; Wavebox treats shortcuts as first-class; SessionBox / Firefox Multi-Account Containers do not lead with keyboard

## Decision

V1 is a **mouse-free account loop during real play**:

1. The operator can **create**, **move to next/previous account**, and **start/run** the targeted account from the keyboard **while a game panel is focused**.
2. Create uses the reducer’s existing default name (`Account N` / `Conta N`). The name dialog is not on the hot path. Rename stays a later mouse action.
3. Next/previous walks the current tab’s full account order (including closed accounts) and wraps. `Mod+1…9` remains a jump, not a substitute for cycle.
4. Start/run starts the targeted (active) account. It does not auto-start every account. Stop, close, delete, wipe, and start-all stay mouse-only.
5. Reserved **modifier chords** for these actions do not reach the game (same class as Chrome `Ctrl+T`). Unmatched keys, including typing in login fields, must still reach the game.
6. Ambition stays a quick win: no customizable keymap, no command palette, no OS-global shortcuts, no requirement to port every existing README shortcut in V1.

Workspace mutations stay the existing verbs (`account/create`, `account/activate`, `account/setStatus`). Isolation, partitions, and “not a bot” remain unchanged.

## Alternatives Considered

### Essence-first: cycle and start only (opportunity B)

- **Benefits:** Smaller; tests the high-frequency cycling moment; create stays the familiar dialog.
- **Costs/risks:** Setup still needs the mouse, so the locked create part of the success metric fails.
- **Why not selected:** User chose A after locking create in the V1 action set.

### Command-layer first slice (opportunity C)

- **Benefits:** Would also fix existing README shortcuts that share the same focus hole; later tab/layout actions plug in.
- **Costs/risks:** Contradicts the quick-win ambition; more design before the loop is proven.
- **Why not selected:** User chose A; C was the rejected larger bet.

### Chrome-only binds (three more `Shell.tsx` listeners)

- **Benefits:** Tiny patch; matches how current shortcuts shipped.
- **Costs/risks:** Independent critique: after the first Start, focus is in the game view; mouse-free dogfood becomes a lie.
- **Why not selected:** Conflicts with direction A and the locked success bar.

### Keep the create name dialog on the shortcut (default name + Enter)

- **Benefits:** Operator can still name before start; matches `Mod+T` opening a tab dialog.
- **Costs/risks:** Current `AccountModal` has no Enter-to-submit; overlay hides running views; create does not activate the new id when another account is already active, so start would hit the old jar.
- **Why not selected:** User accepted default-name create as part of A; rename remains the naming path.

## Consequences

### Positive

- Setup and cycling can stay on the keyboard during live sessions, not only when chrome is focused.
- Default-name create matches isolation-by-UUID (names are labels; duplicates already allowed).
- Scope stays three verbs, so a later command layer is not implied.

### Negative and trade-offs

- A small set of modifier chords will never reach the game, including inside password fields (Chrome-class behavior).
- No name prompt on create; operators who want a name must rename later.
- Existing README shortcuts (`Mod+T`, reload, mute, …) may still fail while a game is focused until a follow-up.
- Stop / start-all / pop-outs remain mouse-only.

### Risks and mitigations

- Game or OS already uses the same modifier chords — stay on modifier chords only (never bare keys); pick chords in techspec; dogfood KPI-03.
- Intercepting keys on sandboxed views looks like input-stealing — allowlist only; swallow only after a match; never log key identity; never inject into the game document; never `globalShortcut`.
- Create-then-start starts the wrong jar because `account/create` does not steal `activeAccountId` — V1 must leave a defined start target (activate the new account as part of the create action’s user-visible result).
- Runtime has not traced focused-view key routing — treat chrome-only as default-dead; verify during implementation, not by README checklist alone.

## Reversibility

High. Shortcuts can be removed without changing partitions or reducer verbs. Default-name create does not remove the existing Plus dialog. The lock-in is operator muscle memory and whichever modifier chords are reserved.

## Follow-ups

- Techspec: chord table, focus routing while a `WebContentsView` is focused, create → defined start target, overlay/dialog behavior.
- Dogfood: KPI-01 mouse-free loop; KPI-03 no stolen typing; existing chrome-focused README shortcuts must not regress.
- Deferred: port remaining README shortcuts onto the same path; start-all / stop; keymap settings; pop-outs.
