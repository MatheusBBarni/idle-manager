# ADR-001: Hybrid public home with gated Windows download

## Status

Accepted

## Date

2026-08-30

## Context

Idle manager has no public player home. The only product story is `README.md`, which leads with contributor setup (`pnpm install` / `pnpm dev`). The GitHub repo `MatheusBBarni/idle-manager` has `homepage: null`, `has_pages: false`, and no Releases. The chosen visitor is a multi-account idle player who needs to understand isolation vs a bot and start a Windows download in one visit.

The user asked for a website (GitHub Pages + Astro as a stated preference), chose a one-page V1, and chose a compounding ambition (structure that can grow later). Independent critique agreed the 30-day download success test is blocked until a GitHub Release NSIS exists, and that hosting binaries on Pages fights GitHub’s 1 GB / 100 GB limits.

This decision locks V1 scope: one landing page plus a download CTA that is not live until a same-repo Release asset exists.

## Decision Drivers

- User-chosen job: public home + Windows download that the README does not provide
- User-chosen V1: one landing page, not docs/changelog/gallery
- User-chosen ambition: foundation for later static pages
- User-chosen success (30 days): first-visit understand isolation vs bot and start a Windows download
- GitHub API 2026-08-30: `releases: []` — no installer to link
- GitHub Pages: static hosting; not for SaaS storefronts; site ≤ 1 GB; soft 100 GB bandwidth/month
- Astro official deploy path: prerendered site via `withastro/action`; `site` + `base` for project pages
- Council consensus: gate the live download CTA on a real Release; do not put NSIS on Pages
- Council dissent (devil’s advocate): a separate page is still unjustified until visitors will hit Pages instead of the Release page

## Decision

V1 is a **hybrid**:

1. **One public landing page** on GitHub Pages, built as a static Astro tree that can add routes later.
2. **Windows download CTA is gated**: it is live only when a real NSIS (or equivalent) asset exists on a GitHub Release of `MatheusBBarni/idle-manager`. Same slice is allowed; a coming-soon/disabled control is allowed until then.
3. **Binaries stay on GitHub Releases**, not on Pages.
4. Copy must state isolation vs bot (not a macro, cheat injector, fingerprint spoof, proxy, or shared cookie jar) and must not add third-party analytics pixels.

Rejected for V1: shipping a live download with no asset; README + Release with no site; gallery/FAQ/docs pages now.

## Alternatives Considered

### Original: ship the one-pager now, even if Releases are empty

- **Benefits:** Shareable URL exists immediately; matches the “public home” job without waiting on packaging.
- **Costs/risks:** First visits hit a dead download; council called this a vanity funnel; 30-day success fails by construction.
- **Why not selected:** User chose Hybrid. Success is a download start; GitHub `releases: []` is verified.

### Essence-first: GitHub Release + README only, no site

- **Benefits:** Smallest path to a downloadable; no second privacy surface; no `/idle-manager` prefix; hits the download half of success.
- **Costs/risks:** README stays contributor-facing (`pnpm dev`); no shareable player home; fails the clarified job that the README does not provide.
- **Why not selected:** User explicitly wanted a public home and a compounding static foundation, not GitHub-only discovery.

### Ambitious: landing + screenshot gallery + FAQ now

- **Benefits:** Closer to competitor marketing sites (Ghost, SessionBox, Wavebox).
- **Costs/risks:** No screenshot inventory (`assets/icon.png` only); extra content before conversion is proven; user already scoped V1 to one page.
- **Why not selected:** Out of V1 by user decision and missing assets.

## Consequences

### Positive

- Player-facing URL can exist without pretending an installer is downloadable.
- Isolation-vs-bot story can live off the README’s contributor path.
- Same Astro tree can grow docs/changelog later without a second host.
- Binaries use GitHub’s intended channel (Releases).

### Negative and trade-offs

- Installer packaging is on the critical path for the 30-day KPI.
- A Pages project site is prefixed (`/idle-manager`) unless a user-site or custom domain is added later.
- Reach is still unknown (1 star, new repo); the site does not create traffic.
- Unsigned NSIS will still face SmartScreen; the page must warn, not imply a signed publisher.

### Risks and mitigations

- Dead CTA if the site ships first — hide or disable Download until a Release asset URL is real.
- Vanity site with no visitors — treat traffic as unknown; do not add analytics pixels that contradict the local-sessions story; measure download starts via GitHub Release asset counts.
- Confusion with anti-detect tools — hero copy must match `README.md` Privacy warning and `AGENTS.md` out of scope.
- Pages bandwidth if binaries were hosted on the site — binaries stay on Releases.
- Devil’s-advocate residual: visitors may still use the repo/Release page — acceptable; the landing is for shareable player positioning, not a monopoly on discovery.

## Reversibility

High. The site can be unpublished from Pages; the Astro tree can be deleted; the Release remains the download source. Lock-in is the project-site URL and any inbound links. Custom domain would increase lock-in and is not part of this ADR.

## Follow-ups

- Publish (or gate on) a Windows GitHub Release before enabling the live Download CTA.
- Confirm project-site `base` (`/idle-manager`) vs a later custom domain (deferred).
- Align GitHub repo license field with `package.json` MIT (public-story mismatch noted by trust advisor).
- PRD should treat installer existence as a launch gate, not a website-only feature.
