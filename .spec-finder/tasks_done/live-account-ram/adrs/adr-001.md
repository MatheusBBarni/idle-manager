# ADR-001: Invisible live-farm diet

## Status

Accepted

## Date

2026-08-31

## Context

A Windows operator who tiles about 3–6 isolated idle-game logins on a shared PC hits machine RAM pressure. Each running account is a live isolated session that must keep progressing. Closing a panel already drops that session’s view and keeps the login. Chrome-style Memory Saver would deactivate unused tabs and reload them, which stops idle progress.

The verified need is not a lower RAM number on a stopped farm. It is: the farm stays alive and the rest of the PC stays usable. V1 must not add Park/Sleep chrome, auto-discard, or shared sessions.

This ADR records the product approach. It does not lock process, throttle, or view implementation.

## Decision Drivers

- User: failure is farm vs PC, not a cosmetic RAM readout
- User: primary operator is a small live farm (about 3–6 accounts, one or two games) on a shared Windows PC
- User: success is a before/after dogfood journal (3-account and 6-account); operator does not close panels just to free the machine
- User: auto-sleep, auto-discard, and merging jars are out; running means ticking
- User: operator should notice a quieter live farm with the same start / close / tile workflow; no new Park control
- User: selected approach A — invisible live-farm diet
- Repository: RAM is already shown; close already destroys the view; off-stage running accounts still cost a live session
- External: Chrome Memory Saver reloads deactivated tabs; that trade is wrong for idle games

## Decision

V1 is an **invisible live-farm diet**:

1. The operator keeps the current start / close / tile / pop-out workflow. No Park, Memory Saver, live-cap, or pressure-nudge chrome.
2. Every account that is **running** keeps progressing, including hidden panels and accounts on other game tabs.
3. Isolation stays one persistent session per account. Processes are not merged to save RAM.
4. Close remains the operator’s way to drop a live session without wiping the login.
5. Success is measured on Windows dogfood: a 3-account and a 6-account farm stay running while other apps stay usable, without closing panels just to free the PC.

If a live session cannot cost less without pausing progress or merging jars, V1 does not ship a fake control. That is a stop, not a pivot to auto-sleep.

## Alternatives Considered

### Diet plus pressure hint

- **User value:** Cheaper live farm plus a non-covering hint when the PC is struggling, asking the operator to close an account.
- **Costs/risks:** Extra chrome; nag mid-session; operator already said V1 should not add a new notice.
- **Why not selected:** User chose A.

### Cap live accounts

- **User value:** PC stays usable by refusing a large farm.
- **Costs/risks:** Fights the 3–6 target; feels like a limiter; close already exists.
- **Why not selected:** User chose A.

### Honest RAM first (clarification B)

- **User value:** Clearer machine vs per-account cost so the operator knows what to close.
- **Costs/risks:** Does not keep a 6-account farm plus other apps by itself.
- **Why not selected:** User chose a quieter live farm, not a readout project.

### Chrome-style auto-sleep / discard

- **User value:** Large RAM win on unused sessions.
- **Costs/risks:** Reloads stop idle progress; contradicts “running means ticking.”
- **Why not selected:** Explicit non-goal.

## Consequences

### Positive

- No new operator state or sleep vocabulary to learn.
- The success bar matches the job: farm plus other apps, not a GB trophy.
- Isolation and close-without-wipe stay the product.

### Negative and trade-offs

- If live sessions cannot get cheaper, V1 has nothing user-visible to ship.
- Off-tab and hidden running accounts still cost a live session (by design).
- RAM chrome stays as-is; dogfood must use Task Manager plus the existing readout.
- Pop-out extra windows and 20-account boxes are not the V1 target.

### Risks and mitigations

- Invisible change is untestable — G-01 requires a written before/after journal on 3 and 6 accounts, not a vibe.
- Implementers pause timers to fake a RAM win — G-02 fails if running accounts reload or stop progressing; that is a ship blocker, not a tweak.
- Scope creeps into Memory Saver chrome when diet is hard — new ADR required; do not silently add Park.

## Reversibility

High. There is no new operator-facing state. Any behind-the-scenes diet can be reverted without a migration. Revisit if dogfood shows no usable-PC gain, or if operators demand an explicit Park after G-01 misses.

## Follow-ups

- TechSpec: how live sessions can cost less without pausing idle progress or merging jars; what to do if they cannot.
- Dogfood: baseline journal before the change; same 3- and 6-account sessions after.
- Deferred: Park/Sleep, pressure hints, live caps, honest whole-app RAM chrome, pop-out diet.
